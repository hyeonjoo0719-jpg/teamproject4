# 05. 설계 결정과 근거

> **2026-09-21 검토 반영:** 자동 점검 통과율은 전체 가이드라인 준수나 사실 정확성이 아니며, 표본 오류 분류는 Claude 단독 판정이다. test는 2026-09-20 00:14 당시 고정한 Stage C 후보에 대해 1회 평가했다. 이후 test에서 관찰한 토론 문제 등을 참고해 dev에서 추가 탐색했다. 후속 개선은 독립 test 검증을 받지 않았으며 새 holdout이 필요하다.

이 프로젝트에서 내린 결정을 한곳에 모았다. 각 항목은 **선택 / 대안 / 근거 / 되돌릴 조건**으로 적는다.
시간순 기록은 `docs/04_experiment_log.md`에 있다. 여기는 "왜 이 값인가"를 찾는 문서다.

## 1. 데이터

### 1.1 분할 — dev 1,500건, test = 공식 valid 전체

- 선택: 공식 train에서 주제×유형 층화로 dev 1,500건 + 토론 전용 dev_debate 200건을 떼고, 나머지 278,292건을 학습에 쓴다. 공식 valid 35,004건은 test로 마지막 1회만 본다
- 대안: dev를 1,000건 또는 2,000건으로, 또는 공식 valid를 쪼개 dev로 쓰기
- 근거 (**B 관찰**): dev 1,500건에서 ROUGE-L의 bootstrap 95% 구간 폭이 약 ±1.0이다(실측: 27.456 [26.468, 28.417]).
  Stage 간 차이는 별도의 paired bootstrap에서 확인했다. 단일 평균의 구간 폭으로 두 모델 차이의 판별 한계를 정할 수는 없다.
  구간 폭은 대략 1/√n로 줄어든다. dev를 6,000건으로 늘리면 폭이 절반(±0.5)이 되지만, 평가 1회가 3분 → 12분이 되고 학습 중 평가가 17회면 51분이 더 든다
- 계산 근거: test 35,004건에서는 같은 지표의 구간 폭이 ±0.2였다(27.154 [26.949, 27.358]). 즉 폭은 건수로 설명된다
- 되돌릴 조건: ±0.5 이하의 차이를 판별해야 하는 실험을 하게 되면 dev를 4,000~6,000건으로 늘린다. 이전 모델도 동일한 새 dev에서 평가해 비교한다
- 분할 고정: `dialogueID` 해시 + seed 20260919. 같은 seed면 재현된다. 중복·누수 검사 통과 (train/dev/dev_debate 교차 0건, train↔valid ID 중복 0건)

### 1.2 Stage 규모 — 2,000 → 20,000 → 278,292

- 선택: 3단계로 늘리고, 각 단계에서 개선이 확인될 때만 다음으로 간다
- 근거 (**A 측정**): 단계마다 dev ROUGE-L(space)이 올랐고 구간이 0을 넘었다

  | 단계 | 학습 건수 | ROUGE-L space | 이전 단계 대비 (95% CI) | 학습 시간 |
  |---|---:|---:|---|---:|
  | A | 2,000 | 22.63 | — | 12.5분 |
  | B | 20,000 | 25.16 | +2.53 [+1.80, +3.23] | 38.3분 |
  | C | 278,292 | 27.33 | +2.17 [+1.36, +2.87] | 371분 |

- 해석 주의: A→B는 데이터(×10)와 epoch(3→2)가 함께 바뀌었다. "데이터 규모만의 효과"가 아니다
- 비용 대비: 데이터를 14배 늘려 +2.2점, 학습 시간은 9.7배. 다음 배수(데이터 없음)는 불가능하다

### 1.3 subset 층화 — 주제×유형, Stage A ⊂ Stage B

- 선택: Stage A(2,000)와 B(20,000)를 같은 salt로 뽑아 A가 B의 부분집합이 되게 했다
- 근거 (**B 관찰**): 주제 분포가 25.4%(개인 및 관계) ~ 4.7%(시사/교육)로 치우쳐 있다. 무작위로 뽑으면 2,000건에서 시사/교육이 94건 내외로 흔들린다.
  포함 관계로 두면 A→B 비교에서 "데이터가 늘었다" 외의 차이를 줄일 수 있다
- 되돌릴 조건: 주제별 성능 차이를 실험 변수로 삼을 때는 층화를 바꾼다

## 2. 입력 형식

### 2.1 직렬화 — `speaker` (`P01: 발화` 줄바꿈 연결)

- 선택: `speaker`. 대안: `plain`(발화만), `turn`(같은 턴 합치기)
- 근거 (**A 측정**): Stage A에서 셋을 비교했고 **차이를 확인하지 못했다**

  | 직렬화 | ROUGE-L space | 기준 대비 (95% CI) | ROUGE-L morph | 기준 대비 (95% CI) |
  |---|---:|---|---:|---|
  | speaker (기준) | 22.632 | — | 41.327 | — |
  | plain | 22.834 | +0.20 [−0.39, +0.78] | 41.343 | +0.02 [−0.53, +0.57] |
  | turn | 22.387 | −0.25 [−0.87, +0.37] | 41.150 | −0.18 [−0.71, +0.37] |

- 유의한 차이를 확인하지 못해 **기준을 유지**했다. 덧붙여 화자 표시는 가이드라인 규칙 2("누가"를 알 수 있게)에 필요한 정보를 입력에 남긴다
- 비용 차이 (**B 관찰**): `speaker`는 `plain`보다 입력이 길다 (train 토큰 p95 262 vs 183, 평균 158.5 vs 102.1). 즉 화자 표시에 토큰을 약 55% 더 쓰고도 점수 이득은 확인되지 않았다
- 되돌릴 조건: Stage B 이상 규모에서 다시 비교해 `plain`이 95% 구간으로 우세하면 바꾼다. 입력 길이를 줄여야 할 때도 1순위 후보다

### 2.2 시스템 태그 — `drop` (`#@시스템#사진#` 삭제)

- 선택: `drop`. 대안: `type` (`[사진]`으로 치환)
- 근거 (**A 측정**): 전체 +0.11 [−0.40, +0.64] (space) — 차이를 확인하지 못했다.
  태그가 있는 dev 199건만 봐도 space +0.81 [−0.41, +2.11] / morph −0.33 [−1.48, +0.95]로 부호가 엇갈린다.
  `type` 쪽은 반복 4-gram 비율이 10.73%로 기준(8.20%)보다 높았다 (정답 6.53%)
- 되돌릴 조건: 오류 분석에서 사진·파일 공유 대화의 누락이 주요 오류로 나오면 다시 비교한다

### 2.3 정규화 — 자모/문장부호 3회 이상 반복을 2회로, 이모티콘 태그 삭제

- 선택: 입력에만 적용. 정답은 원본 그대로
- 근거 (**A 측정**, 2026-09-20): 자모·문장부호 축약을 끄고 비교했다. −0.207 [−0.736, +0.301] (space) / −0.317 [−0.815, +0.159] (morph) — **차이를 확인하지 못했다**
- 다만 끄면 입력이 길어져 잘린 입력이 63건 → 102건으로 늘었다(Stage B 20,000건 기준). 점수 손해는 확인되지 않았고 길이 이득은 있으므로 **유지**한다
- 되돌릴 조건: 구어체 표기를 그대로 살려야 하는 요구가 생기면 끈다 (점수 근거는 어느 쪽에도 없다)

### 2.4 대화 유형 표시 `[토론]`/`[일상]` — 실험 완료, **채택 보류**

- 동기 (**A 측정**): 토론 대화에서 모델이 "~에 대해 토론한다" 형식을 거의 쓰지 않는다. test 188건에서 4.79% (정답 100%), ROUGE-L space 16.02 (일상 27.21)
- 원인 추정: 입력에 유형 정보가 없고, 학습 데이터의 공식 train 기준 0.574%(1,608/279,992)다 (토론 dev 분리 후 실제 학습 비중은 별도)
- 결과 (**A 측정**, 2026-09-20 Stage B 20,000건 규모, 기준선 `b_speaker_drop`과 `type_tag` 하나만 다름)

  | 평가셋 | 지표 | 기준선 | `[토론]/[일상]` 표시 | 차이 (95% CI) |
  |---|---|---:|---:|---|
  | dev 1,500 (일상 99%) | ROUGE-L space | 25.157 | 25.263 | +0.106 [−0.395, +0.623] → **차이 미확인** |
  | dev 1,500 | ROUGE-L morph | 43.538 | 43.346 | −0.192 [−0.666, +0.263] → **차이 미확인** |
  | dev_debate 200 | ROUGE-L space | 12.241 | **17.324** | **+5.083 [+3.310, +7.169]** → 차이 확인 |
  | dev_debate 200 | ROUGE-L morph | 33.257 | **37.507** | **+4.250 [+2.455, +6.156]** → 차이 확인 |
  | dev_debate 200 | '토론' 표현 비율 | 1.5% (3/200) | **19.5% (39/200)** | (비율 구간은 계산하지 않음. 정답 99.5%) |

- 해석: 유형 표시는 **토론 dev에서 점수 개선을 관찰했고** 전체 dev에서는 차이를 확인하지 못했다(토론이 0.57%뿐이므로 예상대로다).
  다만 19.5%는 정답(99.5%)과 여전히 멀다. 유형을 알려줘도 토론 문자열 포함률이 절반 미만이다 → 데이터 부족(20,000건 중 토론 표본 수)이 남은 원인으로 보인다. **확인하지 않았다**
- 관찰: 형식뿐 아니라 내용도 좋아진 사례가 있다 (기준선 "농경사회에서 소보다 말이 더 유용했다고 생각한다" → 유형 표시 "농경사회에서는 소가 우세하지만 인류사 전체를 통틀어서는 말이 더 유용했다고 토론한다")
- 대가: 서빙에서 유형을 입력받아야 한다. 가이드라인 API 규격(2.6.2)에 없는 입력이다. 유형을 모르면 쓸 수 없다
- 판정: **채택 보류.** 토론 대화는 test의 0.54%라 전체 점수 기여가 거의 없고, API 규격을 벗어나는 비용이 있다.
  토론 형식이 요구사항이 되면 채택한다. 그때는 Stage C 규모로 다시 학습해야 한다 (약 6시간)

## 3. 모델·토크나이저

### 3.0 모델 선택 — pko-T5 (제한된 조건의 모델 비교)

- 선택: **인코더-디코더** (T5 계열). 대안: 디코더 전용 (GPT 계열)
- 근거 (**A 측정**): 같은 데이터(2,000건)·같은 dev·같은 유효 배치·같은 beam 4

  | 구조 | 모델 | 파라미터 | 설정 | ROUGE-L space | 반복 4-gram |
  |---|---|---:|---|---:|---:|
  | **인코더-디코더 (선택)** | pko-t5-base | 275.6M | lr 1e-4 | **22.63** | 8.2% |
  | 디코더 전용 | KoGPT2 | 125.2M | lr 5e-5 | 14.71 | 23.6% |
  | 디코더 전용 | KoGPT2 | 125.2M | lr 1e-4 | 13.64 | 20.7% |
  | 디코더 전용 | KoGPT2 | 125.2M | lr 5e-5 + nrng 3 | 13.18 | 0.0% |

  시험한 설정에서 pko-T5가 +7.9점 높았다. 격차가 크더라도 조건 차이에 의한 교란을 제거하지는 못한다
- 반복 관찰: KoGPT2 토큰 4-gram 반복률은 예측 23.6%, 정답 0.53%다. T5는 각각 8.2%, 6.53%다. 서로 다른 토큰 단위이므로 구조 간 직접 비교하지 않는다
- 추가 공정성 한계: 토크나이저와 사전학습 조건이 다르고, T5는 dev 기준 best checkpoint(300스텝), KoGPT2는 마지막 상태(375스텝)를 평가했다. KoGPT2의 기존 실행 코드는 config의 label smoothing 0.1을 전달하지 않아 실제로는 기본값 0.0을 사용했다. 반복 4-gram도 모델별 토큰 단위여서 직접 비교할 수 없다(정답 반복률 T5 6.53%, KoGPT2 0.53%). 따라서 결과는 두 모델과 실행 절차의 비교이며 구조 자체의 인과 효과가 아니다. 2026-09-21 코드 정정으로 smoothing 전달과 프롬프트 잘림 방향을 수정했으나 재학습하지 않았고, 표의 기존 점수는 수정 전 실행 결과다.
- 한계: 파라미터가 2.2배 다르고(같은 크기의 한국어 디코더 전용 공개 모델을 찾지 못함), 2,000건 규모에서만 비교했으며, 프롬프트 형식을 한 가지만 시도했다
- 되돌릴 조건: 같은 크기의 디코더 전용 모델이 생기거나, Stage B 이상 규모에서 격차가 좁혀지면 다시 비교한다

### 3.0.1 전이학습 — 사전학습 가중치를 쓴다 (2026-09-21 실험으로 확정)

- 근거 (**A 측정**): 같은 구조·같은 데이터에서 사전학습 가중치만 뺐을 때 22.632 → **5.927** (16.71점 차이).
  무작위 초기화 모델의 출력은 `아니야 안 것 한다.` 수준으로, 한국어 문장 형태도 만들지 못한다
- 해석: 2,000건으로는 언어를 배울 수 없다. 파인튜닝이 가르치는 것은 "요약하는 법"이다
- 구현: `model.from_scratch` (기본 false)

### 3.1 `paust/pko-t5-base` (275.6M)

- 선택 근거 (**A 측정**): dev 1,500건 토큰화 비교

  | 토크나이저 | vocab | source 평균 토큰 | UNK 비율 | UNK 포함 대화 | 정답 되살림 |
  |---|---:|---:|---:|---:|---:|
  | **pko-t5-base** | 50,358 | 147.9 | **0%** | **0%** | **99.73%** |
  | ke-t5-base | 64,100 | 100.7 | 1.02% | 56.2% | 97.53% |
  | mt5-base | 250,100 | 129.3 | 0.34% | 30.7% | 99.13% |

- 탈락 이유: `ke-t5`는 구어체 글자가 UNK가 되어 **정답 문장조차 복원하지 못한다**(`쌩쌩하다`→`하다`). 복원 못 하는 표현은 생성도 못 한다.
  `mt5`는 vocab 250k라 임베딩만 1.9억 파라미터로 8GB VRAM에 불리하다. 둘 다 개행을 vocab에 두지 않아 `speaker` 포맷의 줄 구분이 사라진다
- 되돌릴 조건: VRAM·시간이 부족하면 `pko-t5-small`(같은 토크나이저라 전처리 변경 없음)

### 3.2 비식별화 태그를 special token으로 추가하지 않음

- 근거 (**B 관찰**): 정규화 후 대화에 남는 태그는 주로 `#@이름#`(train 87,540회, 대화당 평균 0.3회)이고 지금 4토큰이다. 길이 이득이 작고, 새 임베딩은 무작위 초기화라 기준선에서 위험이 크다
- 되돌릴 조건: 출력에 태그 조각(`#@`, `이름#`)이 섞이는 게 주요 오류로 나오면 단일 변수로 비교한다 (현재까지 dev·test 모두 출력 태그 0건)

## 4. 길이·배치·정밀도 (VRAM 8GB 제약)

### 4.1 `max_source_length = 384`, `max_target_length = 64`

- 근거 (**B 관찰**): train 토큰 길이 커버리지 (`speaker` 기준)

  | 상한 | source 커버리지 | | 상한 | target 커버리지 |
  |---:|---:|---|---:|---:|
  | 256 | 94.43% | | 32 | 69.47% |
  | 320 | 98.28% | | 48 | 96.63% |
  | **384** | **99.44%** | | **64** | **99.93%** |
  | 512 | 99.93% | | 96 | 99.999% |

- 실제 잘린 비율: Stage C train 278,292건에서 입력 944건(0.34%), 라벨 242건(0.09%)
- 384를 고른 이유: 512는 커버리지가 0.49%p 늘지만 attention 비용이 길이에 제곱으로 붙는다. 99.4%면 충분하다고 판단했다
- 되돌릴 조건: 긴 대화 슬라이스(test 기준 ROUGE-L 23.27, 짧은 대화 30.88)의 원인이 잘림으로 확인되면 512로 올려 비교한다. **아직 확인하지 않았다**

### 4.2 batch 4 × gradient accumulation 4 (유효 배치 16)

- 근거 (**A 측정**, Part 0 스모크 테스트, `artifacts/env_report.json`)

  | 설정 | peak VRAM | 8GB 안에 들어가나 | 스텝 시간 |

  | batch 8 / len 384 (gradient checkpointing 없음) | 8.54GB | **아니오** | 5.26s |
  | batch 4 / len 384 | 6.12GB | 예 | 0.24s |
  | batch 8 / len 256 | 6.94GB | 예 | 0.28s |

- 실제 학습 peak VRAM: Stage A~C 모두 6.97~7.19GB (총 7.93GB)
- 유효 배치 16 근거 (**A 측정**, 2026-09-20): 8·32와 비교했다 (batch 4 고정, accumulation만 2/4/8)

  | 유효 배치 | 스텝 | 학습 시간 | ROUGE-L space | 기준 대비 (95% CI) | 판정 |
  |---|---:|---:|---:|---|---|
  | 8 | 5,000 | 61분 | 25.332 | +0.175 [−0.274, +0.651] | 차이 미확인 (시간은 1.6배) |

- 되돌릴 조건: VRAM이 더 큰 GPU로 옮기면 batch를 키우고 accumulation을 줄인다 (같은 유효 배치를 유지)

### 4.3 bf16 (fp16 금지)

- 근거 (**C 관행**): T5는 fp16에서 NaN이 나는 것으로 알려져 있다. 이 프로젝트에서 fp16을 시도하지 않았다. GPU가 bf16을 지원한다(compute capability 12.0)
- 관련 관찰 (**A 측정**): 학습 직후 평가와 별도 평가 스크립트(fp32 생성)의 dev 점수가 0.13 다르다(27.325 vs 27.456, 예측 168/1500건 차이).
  bf16 autocast 가설은 재현되지 않았다(172건 차이, 27.426). **원인 미확인**

### 4.4 학습률 1e-4 · label smoothing 0.1 (2026-09-20 검증 완료), warmup 5% / weight decay 0.01 (미검증)

- 학습률 근거 (**A 측정**): Stage B 규모에서 3e-4·5e-5와 비교했다 (한 번에 한 변수, run당 39분)

  | 학습률 | train loss | ROUGE-L space | 기준 대비 (95% CI) | ROUGE-L morph | 판정 |
  |---|---:|---:|---|---:|---|
  | **1e-4 (유지)** | 2.7221 | **25.157** | — | 43.538 | 셋 중 최고 |
  | 3e-4 | 2.6150 | 24.852 | −0.305 [−0.963, +0.374] | 43.193 | 차이 확인 못함 |
  | 5e-5 | 2.8031 | 24.225 | **−0.931 [−1.442, −0.405]** | 42.795 | **더 나쁨** |

  → 1e-4가 관행값이었지만 실제로 셋 중 가장 좋았다. "최적"이라는 뜻은 아니고 **더 좋은 값을 찾지 못했다**는 뜻이다
- **중요한 부수 발견**: lr 3e-4는 train loss가 가장 낮은데(2.615) dev ROUGE는 낮다. 학습 중 최고점도 1,500 스텝에서 나온 뒤 정체했다.
  **loss 개선을 성능 개선으로 읽으면 안 된다.** epoch 3 실험에서도 같은 패턴이었다 (loss는 끝까지 내려가는데 ROUGE는 정체)
- label smoothing 근거 (**A 측정**): 0.0과 비교해 −0.414 [−0.870, +0.011] (space) — 차이를 확인하지 못했지만 구간이 0에 거의 붙어 있고,
  반복 4-gram이 8.8%로 기준(7.67%)보다 높다 → **0.1 유지**.
  주의: 0.0의 train loss 1.334는 기준선 2.722와 비교할 수 없다 (smoothing이 손실 계산식을 바꾼다)
- warmup 5% 근거 (**A 측정**, 2026-09-20): 0%는 −0.224 [−0.622, +0.131], 10%는 −0.042 [−0.407, +0.314] (space).
  **세 값 사이에 유의한 차이를 확인하지 못했다.** 영향 없음이나 동등성을 입증한 것은 아니다
- weight decay 0.01은 여전히 **C 관행**이다. 비교하지 않았다
- 되돌릴 조건: Stage C 규모에서는 순서가 다를 수 있다. 규모를 바꾸면 학습률을 다시 본다

## 5. 학습 종료 조건

### 5.1 epoch 2 (Stage B·C)

- 근거 (**A 측정**): epoch 3 설정으로 다시 돌린 결과 차이를 확인하지 못했다
  - 2 epoch: best 34,000 스텝, dev ROUGE-L space 27.325
  - 3 epoch: 조기 종료로 34,000 스텝에서 멈춤, best 28,000 스텝, 27.262 → 차이 −0.064 [−0.574, +0.445]
  - 1 epoch 이후 dev ROUGE-L은 27 근처에서 ±0.3 흔들리며 정체했다. eval_loss는 끝까지 완만히 내려갔다(2.404)
- 비용: 3 epoch 시도에 6시간 12분을 썼고 얻은 개선은 없다
- 되돌릴 조건: 학습률·배치를 바꾼 뒤에는 epoch도 다시 봐야 한다 (상호작용이 있다)

### 5.2 조기 종료 patience 3 (평가 2,000스텝마다)

- 선택: `early_stopping_patience: 3`, 즉 dev ROUGE-L이 **6,000스텝(약 1시간) 동안** best를 넘지 못하면 멈춘다
- 대안: patience 2(더 빨리 멈춤) / 5(더 오래 봄) / 끄기
- 근거 (**C 관행 + A 측정으로 사후 검토**): 값 자체는 프레임워크 관행을 따랐고 비교하지 않았다. 다만 실행 결과로 다음을 확인했다
  - dev ROUGE-L의 평가 간 변동폭이 ±0.3~0.4다 (예: 3 epoch run에서 26.70 → 26.21 → 26.69 → 26.70 → 26.90)
  - 이 변동폭 때문에 **patience 2였다면 2 epoch run이 12,000스텝 부근에서 멈췄을 것**이다. 그 시점 점수는 25.74로 최종(27.33)보다 1.6점 낮다
  - 반대로 3 epoch run은 patience 3에 걸려 34,000스텝에서 멈췄다. 그때 이미 3번 연속 정체였고, 마지막 3회 평균이 best보다 낮았으므로 **조기 종료가 잘못 끊었다고 볼 근거는 없다**
- 판정 방식의 함정 (**A 측정**): 개선 판정에 임계값이 없어서 **+0.001도 "개선"으로 세어 카운터가 초기화**된다.
  3 epoch run 20,000스텝에서 26.700 vs best 26.699로 초기화된 사례가 실제로 있었다
- 조치 (2026-09-20): `early_stopping_threshold`를 지원하게 고치고 `configs/base.yaml` 기본값을 **0.1**(변동폭의 1/3 수준)로 두었다.
  단 이 값 자체는 비교하지 않았다(**C 관행**). 2026-09-20 하이퍼파라미터 비교 run들은 기준선과 조건을 맞추려고 0으로 껐다

### 5.3 시간 예산 (Stage A 15분 / B 60분 / C 480분)

- 근거 (**B 관찰**): 실측 스텝 속도 0.545초/스텝 × 스텝 수 + 평가 3.2분/회로 계산해 여유를 둔 값이다. 실제로 예산에 걸려 중단된 run은 없다 (Stage C 371분 / 예산 480분)
- 목적: 노트북에서 밤새 돌릴 때 무한정 도는 것을 막는 안전장치다

### 5.4 체크포인트 저장 간격 = 평가 간격 (Stage C 2,000스텝), `save_total_limit: 2`

- 근거 (**B 관찰**): 체크포인트 1개가 약 3.3GB(모델 1.1GB + 옵티마이저 상태). 2개면 6.6GB다.
  2,000스텝 간격이면 중간에 꺼져도 최대 18분 + 평가 3분을 다시 하면 된다. 500스텝 간격이면 손실은 4.5분으로 줄지만 저장 I/O가 4배가 된다
- 근거 (**A 측정**): 실제로 이 값으로 6시간짜리 run 2개를 중단 없이 마쳤다. `--resume` 검증도 통과했다(강제 종료 → 이어하기 결과가 끊지 않은 run과 소수점까지 일치)

## 6. 디코딩

### 6.1 `no_repeat_ngram_size = 0` (기본값 3에서 변경)

- 근거 (**A 측정**), 두 가지로 확인했다
  1. 데이터: train 정답 278,292건 중 **13.37%**가 같은 토큰 3-gram을 두 번 포함한다. 즉 nrng=3이면 정답의 13.4%는 원문 그대로 생성이 **불가능**하다 (n=4: 6.02%, n=5: 1.95%)
  2. 모델: 같은 학습(같은 시드, loss 일치)에서 디코딩만 바꾸니 Stage 0 재현 점검 ROUGE-L이 97.98 → 99.62, 100점이 아닌 건이 12 → 1로 줄었다
- 감시 지표: 반복을 금지하지 않는 대신 예측의 반복 n-gram 비율을 매 run 기록한다. test 기준 예측 4-gram 7.14% / 정답 6.23%로 정답 수준이다
- 되돌릴 조건: 예측 반복 4-gram 비율이 정답의 2배(약 13%)를 넘고 오류 분석에서 반복이 주요 오류로 나오면, 디코딩 비교를 모델 비교와 분리해 다시 한다

### 6.2 beam 4

- 근거 (**A 측정**): 같은 모델에서 beam 1(greedy)과 비교했다

  | 디코딩 | dev ROUGE-L space | morph | 자동 점검 통과율 |
  |---|---:|---:|---:|
  | beam 4 | 27.456 | 45.291 | 97.33% |
  | beam 1 | 25.859 | 44.253 | 96.40% |

- 즉 디코딩만으로 1.6점이 움직인다. **디코딩이 다른 점수는 비교하지 않는다**는 규칙(`docs/03_evaluation.md` 6장)의 근거다
- 비용: beam 4는 생성이 느리다 (test 35,004건 60분). beam 8은 2026-09-21에 시도했으나 자원 제약으로 완료하지 못했다
- 되돌릴 조건: 서빙 응답 시간이 문제 되면 완료한 beam 2 결과(26.940, 167초)와 beam 4(27.456, 180초)를 비교한다 (현재 1건 생성 중앙값 471ms)

### 6.3 `max_new_tokens = 64`, `length_penalty = 1.0`

- `max_new_tokens` 근거 (**B 관찰**): 정답 토큰 길이 p99.9가 63이다(4.1의 표)
- `length_penalty` 근거 (**A 측정**, 2026-09-20): 1.2 / 0.8과 비교했다. 학습 없이 디코딩만 바꿔 dev에서 쟀다

  | lp | 예측 길이 평균 | ROUGE-L space | 차이 (95% CI) |
  |---|---:|---:|---|
  | **1.0 (유지)** | 39.8자 | 27.456 | — |
  | 1.2 | 41.4자 (정답 41.9) | 27.450 | −0.006 [−0.221, +0.224] → 차이 미확인 |
  | 0.8 | 37.5자 | 27.021 | −0.435 [−0.705, −0.174] → 더 나쁨 |

- **얻은 사실**: lp 1.2는 길이를 정답 수준까지 맞추지만 점수는 그대로다. 즉 "예측이 정답보다 짧다"(test 39.5자 vs 42.0자)는 **이 조절만으로 개선된다고 확인하지 못했다**.
  짧은 요약이 문제라면 길이가 아니라 내용 선택(핵심 누락 6/30)을 봐야 한다
- 되돌릴 조건: 길이를 정답 분포에 맞추는 것 자체가 요구사항이 되면 1.2를 쓴다 (점수 근거는 없다)

## 7. 평가 방법

### 7.1 주 지표 ROUGE-L, 토큰화 2종 병기

- 근거 (**A 측정**): 같은 예측·같은 정답인데 기준에 따라 점수가 크게 다르다 (test: space 27.15 / morph 45.35).
  한국어는 조사·어미가 붙어 공백 기준으로는 `영화를`과 `영화가`가 완전히 다른 토큰이 된다. 기준을 안 적으면 비교가 불가능하다

### 7.2 paired bootstrap 1,000회, 95% 구간

- 근거 (**C 관행 + B 관찰**): 1,000회는 관행값이다. 다만 이 프로젝트에서 이 방법이 실제로 판정을 바꿨다.
  Stage A 직렬화 비교에서 점수 차이만 보면 `plain`이 +0.20으로 "더 좋아 보이지만", 구간이 [−0.39, +0.78]이라 차이를 확인하지 못했다
- 구현: 문장별 점수를 같은 인덱스로 리샘플한다 (`src/evaluate.py: paired_bootstrap`)

### 7.3 규칙 기반 자동 점검 통과율을 정답에도 적용

- 근거 (**A 측정**): 자동 판정은 규칙의 근사다. 정답 요약의 자동 점검 통과율이 dev 94.27%, test 95.21%로 100%가 아니다.
  주된 미통과 항목은 "키워드 2개 이상"이며, 다른 항목에도 일부 미통과가 있다. 또한, 가이드라인은 이 조건과 "육하원칙 2요소" 중 하나만 요구한다.
  따라서 모델의 97%는 "정답보다 규칙을 잘 지킨다"가 아니라 **"자체 규칙 통과율이며, 정답과 품질이 동등하다는 근거는 아님"**으로 읽어야 한다

### 7.4 표본 대조 (현재 Claude 단독 판정) 30건을 id 해시로 고정

- 표본 크기 (**A 측정**, 2026-09-20 확대): 30건 → **100건**으로 늘렸다. 같은 해시 순서라 앞 30건은 그대로다

  | 유형 | 30건 | 100건 | 95% 구간(Wilson; AI 판정 오차 제외) |
  |---|---:|---:|---|
  | 사실 오류 | 3 (10%) | **15 (15%)** | 9.3 ~ 23.3% |
  | 핵심 누락 | 6 (20%) | 13 (13%) | 7.8 ~ 21.0% |
  | 화자 혼동 | 3 (10%) | 7 (7%) | 3.4 ~ 13.7% |
  | 형식 위반 | 1 | 1 | 0.2 ~ 5.4% |
  | 무난 | 19 (63%) | 67 (67%) | 57.3 ~ 75.4% |

  구간 폭이 22.1%p → 14.0%p로 좁아졌다. Claude 단독 판정의 관측값은 15/100건이다. 구간에 10% 미만도 포함되며 AI 판정 오차는 반영하지 않았다
- 화자 혼동은 2인 대화 6/91, 3인 이상 1/9로 3인 이상이 더 나쁘다고 볼 근거가 없다 (표본이 작아 판정하지 않는다)
- 고정한 이유 (**A 측정**): 매번 다른 표본을 쓰면 모델 간 비교가 불가능하다. `artifacts/eval/human_check_ids.json`에 30개 id를 저장했다
- 현재 판정자는 **Claude(AI) 1인**이다. 사람 판정이 아니다

### 7.5 test 1회 원칙과 잠금 파일

- 근거 (**C 관행**): holdout 결과가 모델 선택·수정에 영향을 주면 후속 모델에 대한 독립성이 훼손된다. 단순 재집계와 모델 선택을 구분한다
- 구현: `scripts/evaluate_run.py`가 `artifacts/eval/TEST_USED.json`을 만들고, 이미 있으면 test 평가를 거부한다. 끊긴 평가만 `--resume`으로 이어갈 수 있다

## 8. 운영 중 내린 결정

### 8.1 평가 batch 32 → 8

### 통계 해석 보충 (2026-09-21)

문장 bootstrap 구간은 고정된 예측의 평가 표본 변동만 반영한다. 학습 seed 변동·반복적인 dev 탐색·판정자 오차는 별개이며, 유의성 미확인은 동등성 입증이 아니다. 차이의 구간 폭은 비교하는 예측 쌍마다 달라 고정된 ±0.6점 판별 한계는 없다.
