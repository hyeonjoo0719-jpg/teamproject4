## 0. 먼저 알아야 할 용어

### 0.1 과제에 관한 용어

| 용어 | 뜻 |
|---|---|
| **요약 생성(summarization)** | 긴 글을 짧게 줄이는 일. 원문에서 문장을 **골라내는** 방식(추출)과 새 문장을 **써내는** 방식(생성)이 있다. 이 프로젝트는 생성 방식이다 |
| **seq2seq** | "글 넣으면 글 나오는" 신경망 구조. 입력을 읽는 **인코더**와 출력을 쓰는 **디코더**로 나뉜다 |
| **T5** | 구글이 만든 seq2seq 모델 계열. 모든 문제를 "텍스트 → 텍스트"로 푼다. 우리가 쓴 `pko-t5`는 한국어로 사전학습된 T5다 |
| **사전학습 / 파인튜닝** | 사전학습은 대량의 일반 문서로 언어를 배우는 단계(이미 되어 있는 것을 받아 씀). 파인튜닝은 그 모델을 우리 과제(대화→요약)에 맞게 추가 학습하는 것. **이 프로젝트가 한 일은 파인튜닝이다** |

### 0.2 데이터를 다루는 용어

| 용어 | 뜻 |
|---|---|
| **토큰(token)** | 모델이 글을 읽는 단위. 글자도 단어도 아닌 그 중간. 예: `안녕하세요` → `안녕`+`하세요` |
| **토크나이저(tokenizer)** | 글을 토큰으로 쪼개는 도구. 모델마다 정해져 있다 |
| **UNK** | "모르는 토큰". 토크나이저가 처리 못 하는 글자는 UNK가 되고, 그 글자는 **영원히 복원되지 않는다** |
| **train / dev / test** | train은 학습용. dev는 중간 점검·설정 선택용. test는 **최종 성적표용으로 딱 한 번만** 보는 데이터. test 결과를 모델 선택·수정에 사용하면 후속 모델의 독립 검증셋으로 볼 수 없다 |
| **holdout** | 학습에 쓰지 않고 떼어 둔 데이터. 여기서는 test가 그것이다 |
| **누수(leakage)** | 학습 데이터에 test가 섞여 들어가는 사고. 점수가 부풀려진다. 이 프로젝트는 ID 중복 검사로 **0건**을 확인했다 |
| **층화(stratified) 분할** | 주제·유형 비율을 유지한 채 데이터를 나누는 것. 무작위로 나누면 드문 주제가 한쪽에 몰릴 수 있다 |

### 0.3 학습에 관한 용어

| 용어 | 뜻 |
|---|---|
| **배치(batch)** | 한 번에 모델에 넣는 데이터 묶음의 크기. 크면 빠르고 메모리를 많이 쓴다 |
| **gradient accumulation(누적)** | 메모리가 부족할 때 쓰는 기법. 배치 4를 4번 모아서 **유효 배치 16**처럼 학습한다 |
| **스텝(step)** | 모델을 한 번 고치는 단위. 여기서는 유효 배치 16 하나를 처리할 때마다 1스텝 |
| **에포크(epoch)** | 학습 데이터를 처음부터 끝까지 한 바퀴 도는 것 |
| **학습률(learning rate)** | 한 스텝에서 모델을 얼마나 크게 고칠지. 크면 거칠고 작으면 느리다 |
| **warmup** | 학습 초반에 학습률을 0부터 서서히 올리는 구간. 초반 불안정을 줄이려는 관행 |
| **label smoothing** | 정답을 100% 확신하지 않도록 살짝 눌러주는 기법. 과신을 줄인다 |
| **weight decay** | 모델 파라미터가 너무 커지지 않게 누르는 규제 |
| **loss(손실)** | 모델이 정답과 얼마나 다른지를 나타내는 수치. **낮다고 반드시 좋은 요약은 아니다**(이 프로젝트에서 실제로 확인했다. 9.3절) |
| **bf16 / fp16 / fp32** | 숫자를 저장하는 정밀도. fp32가 가장 정확하고 무겁다. **이 프로젝트에서는 fp16을 비교하지 않았고** bf16을 쓴다 |
| **VRAM** | 그래픽카드 메모리. 이 노트북은 8GB(실제 7.93GB)라 여기에 맞춰 모든 설정을 정했다 |
| **체크포인트** | 학습 도중 저장한 모델 상태. 컴퓨터가 꺼져도 여기서 이어갈 수 있다 |
| **조기 종료(early stopping)** | 점수가 더 오르지 않으면 학습을 일찍 멈추는 장치 |

### 0.4 생성(디코딩)에 관한 용어

모델은 단어를 하나씩 이어 붙여 문장을 만든다. 그 방식을 **디코딩**이라 한다.

| 용어 | 뜻 |
|---|---|
| **greedy** | 매 순간 가장 그럴듯한 단어 하나만 고름. 빠르지만 근시안적 |
| **beam search (beam 4)** | 후보 문장 4개를 동시에 이어가며 전체적으로 가장 그럴듯한 것을 고름. 느리지만 대체로 좋다 |
| **no_repeat_ngram_size (nrng)** | "같은 단어 n개 묶음을 두 번 쓰지 마라"는 금지 규칙. 반복을 막지만 **정답에 원래 있는 반복까지 막는다**(6.3절 — 실제로 정답의 13.37%를 막고 있었다) |
| **length_penalty (lp)** | 긴 문장을 선호할지 짧은 문장을 선호할지 조절하는 값. 1.0이 기본 |

**중요**: 디코딩만 바꿔도 점수가 움직인다(이 프로젝트에서 beam 4 → 1로 바꾸니 1.6점 하락).
그래서 **점수를 적을 때는 항상 디코딩 설정을 함께 적는다.**

### 0.5 평가에 관한 용어

| 용어 | 뜻 |
|---|---|
| **ROUGE** | 생성한 요약과 정답 요약이 **얼마나 겹치는지** 세는 지표. ROUGE-1은 단어 단위, ROUGE-2는 2단어 묶음, **ROUGE-L은 순서를 지킨 최장 공통 부분**을 본다. 이 프로젝트의 주 지표는 ROUGE-L |
| **공백 기준 / 형태소 기준** | 겹침을 셀 때 무엇을 한 단위로 볼지. 공백 기준은 띄어쓰기로 자른다(`영화를`과 `영화가`는 완전히 다름). 형태소 기준은 `영화`+`를`로 쪼개 공통 형태소를 센다(의미·사실 정확성은 직접 측정하지 않음). **같은 요약도 기준에 따라 점수가 크게 다르다** |
| **신뢰구간(95% CI)** | 가정하에 같은 절차를 반복할 때 참값을 포함하는 비율이 95%인 방식으로 구성한 구간. 두 모델의 차이 구간이 0을 포함하면 해당 비교에서 유의한 차이를 확인하지 못한 것이다 |
| **paired bootstrap** | 두 모델을 비교할 때, 같은 평가 문장들을 무작위로 다시 뽑기를 1,000번 반복해 차이의 구간을 구하는 방법. 점수 차이만 빼서 비교하는 것보다 훨씬 정직하다 |
| **슬라이스(slice) 평가** | 전체 평균이 아니라 주제별·길이별로 쪼개서 보는 것. 평균은 약점을 숨긴다 |

## 1. 무엇을 만들려고 했나

AI Hub 「한국어 대화 요약」 데이터로 **카톡 같은 대화를 한 문장으로 요약**하는 모델을 만든다.
가이드라인 PDF(데이터 제작 지침)의 규칙을 그대로 따르는 것이 목표다.

**가이드라인이 요구하는 요약의 조건 4가지**

1. 요약은 **한 문장**
2. 육하원칙 2요소 이상 + "누가"를 알 수 있게, 또는 대화 키워드 2개 이상 포함
3. 일상 대화는 "~하다/한다" 체, 토론 대화는 "(누가) ~에 대해서 토론한다"
4. 요약문에 비식별화 태그(`#@이름#` 등)를 넣지 않는다

> **비식별화 태그란?** 개인정보를 가린 자리표시자다. 원본 대화의 이름은 `#@이름#`, 사진 공유는 `#@시스템#사진#`처럼 바뀌어 있다.

**입출력 예시** (설명용 예시; 실제 test 예측으로 검증되지 않음)

```
P01: 내일 몇 시에 만날까?
P02: 7시 어때? 강남역에서
P01: 좋아 그때 저녁 먹자
→ 내일 7시에 강남역에서 만나서 저녁을 먹기로 했다.
```

## 3. Part 1 — 데이터가 어떻게 생겼는지 먼저 본다

**왜 하나**: 데이터 성질을 모르고 설정을 정하면 전부 추측이 된다. 입력 길이 상한, 출력 길이 상한, 무엇을 지표로 삼을지가 전부 여기서 나온다.

**전체 규모**

| 구분 | 건수 |
|---|---:|
| 공식 train | 279,992 |
| 공식 valid (= 우리의 test) | 35,004 |

**대화의 생김새** (train 전수 측정)

| 항목 | 값 |
|---|---|
| 발화 수 | 평균 11.3개, p95 18개 |
| 대화 길이 | 평균 120.6자, 중앙값 108자, p95 225자 |
| 요약 길이 | 평균 42.0자, 중앙값 40자, p95 69자 |
| 참여자 수 | 2인 93.3%, 3인 6.2%, 4인 이상 0.5% |

> **p95란?** 100개를 줄 세웠을 때 95번째 값. "대부분이 이 아래"라는 뜻. 상한을 정할 때 쓴다.

**설계를 바꾼 결정적 사실 4가지**

| 사실 | 수치 | 그래서 무엇을 했나 |
|---|---|---|
| **토론 대화가 거의 없다** | 1,608건 / **0.574%** | 유형별 형식 학습을 기대하지 않기로 했다 → 실제로 못 배웠다 (7.4절) |
| **요약문에 태그가 없다** | **0건** (전수) | 모델 출력에 `#@`가 나오면 그 자체로 오류 → 자동 점검 지표로 삼았다 |
| **모든 요약이 마침표로 끝난다** | 279,992건 전부 | 문장 종결 판정을 규칙으로 만들 수 있다 |
| **대화에는 태그가 많다** | `#@이름#` 87,540회, `#@시스템#` 41,919회 | 태그를 어떻게 처리할지가 전처리의 핵심 변수가 됐다 (6.4절) |

**주제 분포 (불균형하다)**: 개인 및 관계 25.4% / 주거와 생활 16.1% / 여가 생활 12.6% / 식음료 10.8% / 상거래 9.4% / 행사 7.6% / 일과 직업 7.3% / 미용과 건강 6.1% / 시사·교육 4.7%

**누수 검사**: train과 valid의 `dialogueID` 교차 중복 **0건**. ID 교차 중복은 없었다. 이것만으로 내용·참여자 수준의 누수를 모두 배제하지는 못한다.

**토큰 길이** (`pko-t5` 기준, 화자 표시를 붙인 입력)

| 입력 상한 | 잘리지 않는 비율 | | 출력 상한 | 잘리지 않는 비율 |
|---:|---:|---|---:|---:|
| 256 | 94.43% | | 32 | 69.47% |
| 320 | 98.28% | | 48 | 96.63% |
| **384 (선택)** | **99.44%** | | **64 (선택)** | **99.93%** |
| 512 | 99.93% | | 96 | 99.999% |

→ **입력 384 / 출력 64로 확정.** 512로 올리면 0.49%p 더 살릴 수 있지만, 계산량은 길이의 제곱으로 늘어난다.

### test를 보지 않기 위해 정한 규칙

test(공식 valid)에서 **건수와 ID, 주제·유형 분포까지만** 보고, 요약문 내용·길이 통계는 Part 5 최종 평가 전까지 열지 않기로 했다.
길이 통계가 필요하면 train에서 낸다. 이 제한은 최초 test 평가 전까지의 규칙이다. 평가 이후 test 사례를 후속 탐색에 참고했다.

## 4. Part 2 — 데이터 준비 (전처리와 분할)

### 4.1 분할

| 이름 | 출처 | 건수 | 용도 |
|---|---|---:|---|
| train | 공식 train에서 분리 | 278,292 | 학습 |
| dev | 공식 train에서 주제×유형 층화 | 1,500 | 중간 점검, 설정 선택 |
| dev_debate | 남은 토론 대화에서 | 200 | 토론 형식 확인용 (토론이 dev에 8건뿐이라 따로 뽑았다) |
| test | 공식 valid 전체 | 35,004 | 최종 1회 |

분할은 `dialogueID`를 해시로 섞어 고정했다(seed 20260919). 같은 코드를 다시 돌리면 같은 분할이 나온다.
검증: train/dev/dev_debate 교차 중복 **0건**, 합계 279,992건 보존 확인.

> **dev를 왜 1,500건으로 했나?** 뒤에서 실제로 계산했다. dev 1,500건에서 ROUGE-L 신뢰구간 폭이 약 ±1.0이다.
> test 35,004건에서는 ±0.2였다. 즉 건수가 많을수록 구간이 좁아진다. 단, 평균의 구간 폭과 두 모델 차이의 구간 폭은 다르다. 특정 차이의 판별 여부는 해당 예측 쌍의 paired bootstrap으로 판단한다.

### 4.2 전처리 — 입력만 손대고 정답은 건드리지 않는다

| 처리 | 내용 |
|---|---|
| 직렬화 | 발화들을 한 덩어리 텍스트로 만드는 방식. `P01: 발화` 형태를 줄바꿈으로 연결 (`speaker` 방식) |
| 시스템 태그 | `#@시스템#사진#`을 삭제 (`drop`) |
| 이모티콘 태그 | `#@이모티콘#` 삭제 |
| 반복 축약 | `ㅋㅋㅋㅋㅋ` → `ㅋㅋ`, `!!!!!` → `!!` |
| 접두어 | 입력 앞에 `대화 요약: `을 붙인다 (T5에 "이 일을 하라"고 알려주는 관행) |

**정답 요약문은 원본 그대로 쓴다.** 정답까지 정규화하면 평가가 왜곡된다.

이 처리들이 옳은지는 나중에 전부 실험으로 확인했다(직렬화·태그는 6.4절, 정규화 축약은 9.2절).

## 5. Part 3 — 어떤 모델을 쓸 것인가

### 5.1 토크나이저로 모델을 골랐다

**점수가 아니라 "정답을 복원할 수 있는가"로 골랐다.** 토크나이저가 어떤 글자를 UNK로 만들면, 그 표현은 **학습해도 생성할 수 없다.**

| 토크나이저 | vocab | 입력 평균 토큰 | UNK 비율 | UNK 포함 대화 | 정답 되살림 |
|---|---:|---:|---:|---:|---:|
| **paust/pko-t5-base (선택)** | 50,358 | 147.9 | **0%** | **0%** | **99.73%** |
| KETI-AIR/ke-t5-base | 64,100 | 100.7 | 1.02% | 56.2% | 97.53% |
| google/mt5-base | 250,100 | 129.3 | 0.34% | 30.7% | 99.13% |

> **"정답 되살림"이란?** 정답 문장을 토큰으로 쪼갰다가 다시 합쳤을 때 원래 문장이 그대로 나오는 비율.

**탈락 이유 (수치와 실제 사례)**

- `ke-t5`: 입력이 32% 짧아지는 장점이 있지만 구어체 글자(`걍`, `넹`, `앜`)가 UNK가 된다. **정답 문장조차 망가진다** — `쌩쌩하다`→`하다`, `얄밉게`→`얄게`, `깼다`→`다`
- `mt5`: UNK는 적지만 30.7%의 대화에 UNK가 있고, vocab 250k라 임베딩만 1.9억 파라미터를 먹는다(8GB에 불리)
- 두 모델 다 **개행 문자를 vocab에 두지 않아** 우리 입력 형식의 줄 구분이 사라진다

### 5.2 임베딩 — 토큰이 숫자 벡터가 되는 층

> **임베딩(embedding)이란?** 토큰 하나를 숫자 벡터 하나로 바꾸는 표(look-up table)다.
> 모델은 글자를 직접 보지 못하고 이 벡터만 본다. 표의 크기는 `vocab 수 × 벡터 차원`이다.

우리 모델(`pko-t5-base`)의 임베딩

| 항목 | 값 |
|---|---|
| vocab (토큰 종류) | 50,358 |
| 벡터 차원 `d_model` | 768 |
| 임베딩 파라미터 | 50,358 × 768 = **38.7M** |
| 전체 파라미터 대비 | **14.0%** (전체 275.6M) |

**임베딩이 모델 선택에 직접 영향을 줬다.**
`mt5-base`는 vocab이 250,100이라 임베딩만 250,100 × 768 ≈ **1.9억 파라미터**다. 우리 모델 전체(2.76억)의 70%에 해당한다.
VRAM 8GB에서는 이 비용이 그대로 학습 가능 배치를 깎아먹는다. 그래서 UNK가 적음에도 탈락시켰다(5.1절).

**새 토큰을 추가하면 임베딩 행이 늘어난다.** 이 프로젝트에서 실제로 겪은 사례가 둘이다.
- 비식별화 태그를 special token으로 추가하는 안 → 새 행은 **무작위 초기화**라 기준선에서 위험이 크다고 보고 하지 않았다 (5.5절)
- 구조 비교용 KoGPT2는 토크나이저의 `</s>` id가 임베딩 행 수를 벗어나 있어서(51200 vs 51200행) **임베딩을 51,201행으로 늘려야** 학습이 가능했다 (9.6절)

### 5.3 구조 — 인코더-디코더를 골랐다

> **인코더-디코더**: 입력 전용 신경망(인코더)이 대화 전체를 읽어 벡터로 만들고, 출력 전용 신경망(디코더)이 그 벡터를 보며 요약을 한 토큰씩 쓴다. 디코더는 인코더의 전체 출력 위치를 참조한다(cross-attention). 디코더 자체의 생성은 이전 출력 토큰에 조건을 둔다.
> **디코더 전용**: 대화와 요약을 한 줄로 이어 붙이고, **왼쪽에서 오른쪽으로만** 읽으며 다음 토큰을 예측한다. GPT 계열이 이 구조다.

`paust/pko-t5-base`의 구조

| 항목 | 값 |
|---|---|
| 인코더 | 12층, hidden 768, head 12, FFN 2048 |
| 디코더 | 12층 (+ 인코더를 보는 cross-attention) |
| 전체 파라미터 | 275.6M |

**왜 요약에 인코더-디코더가 유리한가 (가설)**
- 요약은 "입력을 다 읽고 → 짧게 다시 쓰는" 일이다. 인코더가 대화 **전체를 양방향으로** 본 뒤 디코더가 쓰기 시작한다
- 디코더 전용의 입력 표현은 causal attention으로 계산하지만, 요약을 생성하는 위치에서는 앞선 대화 전체를 참조할 수 있다. 대화와 요약이 하나의 시퀀스에 놓인다는 차이가 있다

이건 가설이므로 **두 모델을 일부 공통 조건에서 비교했다 (모델 크기·토크나이저·학습 옵션·체크포인트 선택은 다름)**: 인코더-디코더 22.63 vs 디코더 전용 14.71 (+7.9점) → 9.6절.

### 5.4 전이학습 — "썼다"가 아니라 "효과를 쟀다"

> **전이학습(transfer learning)**: 대량의 일반 문서로 미리 학습된 모델을 가져와, 우리 과제 데이터로 이어서 학습하는 것. 이 프로젝트의 파인튜닝이 그것이다.

사전학습이 실제로 얼마나 기여하는지 확인하려고, **같은 구조·같은 토크나이저·같은 데이터(2,000건)·주요 학습 설정**에서
사전학습 가중치만 빼고(무작위 초기화) 학습했다.

| 초기화 | train loss | dev ROUGE-L 공백 | 생성 예시 |
|---|---:|---:|---|
| **사전학습 가중치** | 2.8973 | **22.63** | 여러 명이서 만나야 그 사람의 성격과 성질을 제대로 알 수 있다고 한다. |
| 무작위 초기화 | 44.23 | **5.93** | 아니야 안 것 한다. |

- 이 학습 예산에서 ROUGE-L 차이는 **16.71점**(22.63 대 5.93)이다. 품질이 3.8배라는 뜻은 아니다. 무작위 초기화 모델은 한국어 문장 형태조차 만들지 못하고 같은 말을 반복한다
- 해석: 2,000건으로는 언어 자체를 배울 수 없다. 우리가 파인튜닝으로 가르치는 것은 "요약하는 방법"이고, "한국어"는 사전학습이 이미 준 것이다
- 구현: `configs/base.yaml`의 `model.from_scratch`

### 5.5 비식별화 태그를 새 토큰으로 추가할까? → 하지 않았다

- 추가하면 `#@이름#`(현재 4토큰)이 1토큰이 된다. 하지만 대화당 평균 0.3회라 길이 이득이 작다
- 새로 만든 토큰의 임베딩은 **무작위로 시작**하므로 기준선에서는 위험이 크다
- 되돌릴 조건: 출력에 태그 조각이 섞이는 게 주요 오류로 나오면 재검토 → **실제로는 dev·test 모두 태그 출력 0건이라 재검토할 이유가 없었다**

## 6. Part 4 — 학습 (작게 시작해서 키운다)

### 6.1 왜 단계적으로 키우나

전체 27만 건을 바로 돌리면 6시간이 걸리고, 잘못됐을 때 원인을 찾을 수 없다.
그래서 **64건 → 2,000건 → 20,000건 → 278,292건** 순서로 올리고, 각 단계에서 "다음으로 갈 근거"를 확인했다.

### 6.2 Stage 0 — 파이프라인이 제대로 동작하는가 (64건, 2분)

**목적**: 성능이 아니라 **버그 확인**. 64건만 40바퀴 돌려서 모델이 그걸 통째로 외우는지 본다.
외우지 못하면 모델 문제가 아니라 코드 문제다(라벨이 잘못 붙었거나, 문장 끝 표시가 없거나, 점수 계산이 틀렸거나).

**결과**: 같은 64건 재생성 ROUGE-L **99.62** (기준 90 이상). loss 2.15 → 0.0003. 학습 126초, peak VRAM 5.99GB.
→ 데이터 로딩부터 점수 계산까지 전 과정이 정상이라는 근거를 얻었다.

> 이 점수는 **학습한 데이터를 다시 맞춘 것**이라 성능이 아니다. 문서에서는 "재현 점검"이라고 부른다.

### 6.3 Stage 0에서 발견한 문제 — 기본 디코딩 설정이 정답을 막고 있었다

100점이 아닌 12건을 살펴보니, 정답에 같은 표현이 두 번 나오는 경우였다.
예: 정답 `아빠를 닮아서 … 엄마를 닮아서` → 모델 출력 `엄마를 닮았다고`

원인은 `no_repeat_ngram_size=3`(같은 3토큰 묶음 반복 금지)이라는 **프로젝트에 설정된 값**이었다.

**데이터로 확인**: train 정답 278,292건 중 같은 3-gram이 반복되는 비율

| n | 반복 포함 비율 |
|---:|---:|
| 2 | 44.17% |
| **3** | **13.37%** |
| 4 | 6.02% |
| 5 | 1.95% |

→ nrng=3이면 **정답의 13.4%는 원문 그대로 생성하는 것이 원천적으로 불가능**하다.

**모델로 확인**: 같은 학습 결과에서 디코딩만 바꿨더니

| 설정 | 재현 ROUGE-L | 100점이 아닌 건 |
|---|---:|---:|
| nrng 3 | 97.98 | 12 / 64 |
| **nrng 0 (변경)** | **99.62** | **1 / 64** |

→ **nrng 0으로 확정.** 대신 반복 생성이 늘어나는지 감시하려고, 매 실행마다 예측의 반복 n-gram 비율을 기록하게 했다.
(최종 test에서 예측 4-gram 반복 7.14% vs 정답 6.23% — 동등성이나 반복 오류 부재는 미입증)

### 6.4 Stage A — 입력 형식을 정한다 (2,000건 × 4회, 50분)

**한 번에 한 가지만 바꿔서** 비교했다. 판정은 paired bootstrap 95% 구간.

| 비교 | ROUGE-L 공백 | 차이 (95% CI) | 판정 |
|---|---:|---|---|
| `speaker` (기준, `P01: 발화`) | 22.632 | — | — |
| `plain` (발화만) | 22.834 | +0.20 [−0.39, +0.78] | 차이를 확인하지 못함 |
| `turn` (같은 턴 합치기) | 22.387 | −0.25 [−0.87, +0.37] | 차이를 확인하지 못함 |
| 시스템 태그 `type` (`[사진]`으로 치환) | 22.741 | +0.11 [−0.40, +0.64] | 차이를 확인하지 못함 |

**결론: 기준(`speaker`/`drop`) 유지.** 근거는 세 가지다.

1. 셋 모두 유의한 차이를 확인하지 못했으므로 **바꿀 이유가 없다**
2. 화자 표시는 가이드라인 규칙 2("누가"를 알 수 있게)에 필요한 정보를 입력에 남긴다
3. `type` 쪽은 반복 4-gram이 10.73%로 기준(8.20%)보다 높았다 (정답 6.53%)

> **"유의한 차이를 확인하지 못했다"도 결과다.** 점수만 보면 `plain`이 +0.20으로 좋아 보이지만, 구간이 0을 포함하므로 우연일 수 있다.
> 다만 `speaker`는 입력이 55% 길다(평균 158.5 vs 102.1 토큰). 길이를 줄여야 할 상황이 오면 1순위 후보다.

### 6.5 사고 — 학습 중 컴퓨터가 꺼졌다 (2026-09-19 14:24)

Stage A 첫 시도에서 dev 평가 도중 시스템이 다운됐다.

**남은 기록으로 확인한 것**

- 평가 속도가 배치당 2초 → **60~130초**로 느려지다가 16/47 배치에서 멈춤
- Windows 이벤트: bugcheck `0x101 CLOCK_WATCHDOG_TIMEOUT`(CPU 코어 응답 없음) + WHEA 치명적 하드웨어 오류
- 직전 10분간 Wi-Fi·블루투스 오류 반복

**조치**: 평가 batch를 32 → 8로 낮췄다.
이유는 beam 4 × batch 32 = 한 번에 128개 문장을 생성하느라 VRAM 8GB를 넘겨 시스템 공유 메모리로 넘어갔을 가능성이다.
**확정하지는 못했다**(노트북 발열·전원 문제일 수도 있다). 다만 조치 후 같은 구간을 배치당 0.6초로 통과했고, 이후 6시간짜리 학습을 두 번 포함해 다운이 재발하지 않았다.

### 6.6 Stage B → C — 데이터를 늘린다

| 단계 | 학습 건수 | 스텝 | 학습 시간 | ROUGE-L 공백 | 이전 단계 대비 (95% CI) |
|---|---:|---:|---:|---:|---|
| A | 2,000 | 375 | 12.5분 | 22.63 | — |
| B | 20,000 | 2,500 | 38분 | 25.16 | **+2.53 [+1.80, +3.23]** |
| C | 278,292 | 34,788 | **371분** | 27.33 | **+2.17 [+1.36, +2.87]** |

**두 단계 모두 구간이 0을 넘었다 = 데이터를 늘린 효과를 확인했다.**

주의할 점 두 가지를 기록해 뒀다.
- A→B는 데이터(×10)와 epoch(3→2)가 **함께** 바뀌었다. 데이터만의 효과로 말할 수 없다
- Stage C는 마지막 평가(34,000스텝)가 최고점이었다. 즉 **수렴을 확인하지 못했다** → 이래서 나중에 3 epoch를 시도했다(9.1절)

### 6.7 6시간짜리 학습을 위한 준비 — 이어하기 기능

Stage C는 6시간이 걸리는데, 전날 시스템 다운을 겪었다. 기존 코드는 끊기면 **처음부터** 다시 해야 했다.

**추가한 것**: `python scripts/train.py --resume <run 폴더>`
- 저장이 끝까지 된 체크포인트에서 모델·옵티마이저·학습률 스케줄·난수 상태·데이터 순서를 그대로 이어받는다
- 저장 도중 꺼져서 생긴 **반쪽 체크포인트는 건너뛴다**(`trainer_state.json`과 `optimizer.pt`가 모두 있는 것만 인정)

**검증 방법**: 작은 설정(160건, 20스텝)으로 (A) 끊지 않은 학습과 (B) 10스텝 직후 `taskkill /F`로 강제 종료 후 이어한 학습을 비교했다.
→ step 15·20의 loss, grad_norm, eval_loss, 최종 ROUGE가 **소수점 끝자리까지 일치**했다.

## 7. Part 5 — 평가 (점수 하나가 아니라 "무엇을 왜 틀리는가")

### 7.1 평가를 이렇게 설계한 이유

ROUGE는 **어휘가 겹치는지**만 본다. 사실을 틀렸는지, 가이드라인 형식을 지켰는지는 모른다.
그래서 4가지를 함께 본다: ① ROUGE(2가지 기준) ② 규칙 기반 자동 점검 통과율 ③ 슬라이스별 점수 ④ Claude가 읽고 분류한 오류 유형 (사람 검증 미실시).

### 7.2 최종 성적 (test = 공식 valid 35,004건, 최초이자 유일한 1회)

| 평가셋 | 건수 | ROUGE-L 공백 [95% CI] | ROUGE-L 형태소 [95% CI] | 자동 점검 통과율 (정답의 자동 점검 통과율) |
|---|---:|---|---|---|
| dev | 1,500 | 27.46 [26.47, 28.42] | 45.29 [44.44, 46.10] | 97.3% (94.3%) |
| **test** | **35,004** | **27.15 [26.95, 27.36]** | **45.35 [45.16, 45.54]** | **97.0% (95.2%)** |

dev와 test의 95% 구간은 겹치지만, dev 평균은 test 구간 밖이다. 평균 차이만으로 과적합의 유무를 확정할 수 없다.

- 출력에 태그 0건, 빈 출력 0건
- 예측 길이 평균 39.5자 (정답 42.0자)
- 참고선: 가이드라인 시범 모델 ROUGE-L 19.547 — 단, **원문에 토큰화 기준이 없어 비교가 아니라 참고다**

> test는 코드로 잠갔다(`artifacts/eval/TEST_USED.json`). 이미 사용했으므로 앞으로 모델 선택은 dev로만 한다.

### 7.3 규칙 기반 자동 점검 통과율 — 정답에도 같은 잣대를 댔다

| 항목 | 모델 예측 | 정답(기준선) |
|---|---:|---:|
| 한 문장 | 99.99% | 99.98% |
| 태그 없음 | 100% | 100% |
| 길이 10~150자 | 100% | 100% |
| 키워드 2개 이상 겹침 | 98.16% | 95.35% |
| 반복 없음 | 99.43% | 99.88% |
| '~다' 종결(일상) | 99.88% | 100% |
| **전 항목 통과** | **97.02%** | **95.21%** |
| 토론 문자열 포함 (토론 188건만) | **4.79%** | **100%** |

> **왜 정답도 100%가 아닌가?** 자동 점검은 규칙의 근사다. 가이드라인은 "키워드 2개" 또는 "육하원칙 2요소" 중 하나만 요구하는데,
> 우리 점검기는 키워드만 본다. 그래서 모델의 97%는 "정답보다 낫다"가 아니라 **"자체 규칙 통과율이며, 정답과 품질이 동등하다는 근거는 아님"**으로 읽어야 한다.

| 기준 | 값 | 건수 | ROUGE-L 공백 |
|---|---|---:|---:|
| 대화 유형 | 일상 대화 | 34,816 | 27.21 |
| | **토론 대화** | **188** | **16.02** |
| 대화 길이 | 짧음 | 11,624 | **30.88** |
| | 중간 | 11,698 | 27.33 |
| | **김** | **11,682** | **23.27** |
| 참여자 | 2인 | 32,642 | 27.23 |
| | 3인 이상 | 2,362 | 26.17 |
| 주제 | 최고: 식음료 | 3,773 | 27.73 |
| | 최저: 상거래(쇼핑) | 3,288 | 25.94 |

**두 가지 약점이 드러났다.**

1. **토론 대화**: "토론" 문자열을 포함한 비율이 **4.79%** (정답 100%). 토론 문자열 포함률이 낮았다 (형식 전체 미검증)

### 7.6 평가 중 발견한, 아직 설명하지 못한 것

같은 체크포인트·같은 디코딩인데 **학습 직후 평가는 27.325, 별도 평가 스크립트(fp32)는 27.456**으로 0.13 차이가 났다(예측 168/1,500건이 다름).

- **원인 미확인.** Part 5 수치는 모두 평가 스크립트 기준으로 통일했고, Stage 간 비교는 모두 학습 직후 평가라 조건이 같다

### 7.7 베이스라인부터 자동 지표와 AI 판정이 어떻게 달라졌나

점수 외에 **자동 검토 신호가 어떻게 변하는지**를 보려고, 같은 dev 1,500건에 같은 잣대를 대고 단계별로 쟀다.
자동으로 계산되는 오류 신호는 `src/error_probe.py`에 구현했다.

**방법 1 — dev 전체 1,500건 (자동 지표 변화이며 실제 오류 감소와 구분한다)**

| 지표 | Stage A (2천) | Stage B (2만) | Stage C (28만) | 정답 요약 |
|---|---:|---:|---:|---:|
| ROUGE-L 0점 비율 (↓) | 19.0% | 15.2% | **13.0%** | 0% |
| ROUGE-L 10점 미만 (↓) | 25.9% | 22.2% | **20.1%** | 0% |
| 규칙 기반 자동 점검 통과율 (↑) | 94.3% | 96.3% | **97.3%** | **94.27%** |
| 정답 내용어 포함률 (↑) | 45.4% | 50.9% | **54.8%** | 100% |
| 화자표시·태그 누출 (↓) | 0% | 0% | 0% | 0% |

- 핵심 누락의 대리 지표(정답 내용어 포함률)가 45.4% → 54.8%로 올랐다

  정상적인 바꿔 쓰기 증가와 환각 증가를 이 값만으로 구분할 수 없다. 어느 원인인지 확인하지 않았다

**방법 2 — 고정 30건을 단계별 모델로 다시 판정 (표본이 작다)**

| 유형 | Stage A | Stage B | Stage C |
|---|---:|---:|---:|
| 무난 | 20 | 22 | 19 |
| 사실 오류 | 4 | 4 | 3 |
| 핵심 누락 | 5 | 1 | 6 |
| 화자 혼동 | 1 | 3 | 3 |
| 반복 | **1** | 0 | 0 |
| 형식 위반 | 0 | 0 | 1 |
| 오류 1개 이상 | 10 | 8 | 11 |

**정직한 해석**: 유형별 개수는 **단조롭게 줄지 않는다.** 30건은 한 유형당 1~2건 차이로 순서가 바뀌는 크기이고 판정자도 Claude 하나이며 사람 검증은 없다.
따라서 자동 지표 개선과 실제 오류 감소를 구분한다. 30건 판정에서는 오류 감소를 확인하지 못했으며, 오류의 성격을 살피는 데 사용한다.
다만 **고정 30건에서는 B·C의 반복 오류가 관찰되지 않았다**: Stage A의 `비가 와서 싫다고 하자 비가 와서 싫다고 한다` 같은 사례가 B·C에는 없다.

**단계별로 실제 요약이 어떻게 바뀌는가** (같은 대화, 정답: *아이패드와 애플 펜슬도 써봤는데 그냥 연필 쓰는 느낌이다*)

## 9. 추가 검증 — "관행대로 정한 값"을 실제로 확인했다

여기까지의 설정 중 상당수는 **"보통 그렇게 한다"는 이유로 정한 값**이었다. 그래서 하나씩 실제로 비교했다.
하이퍼파라미터 비교는 주로 Stage B, epoch 비교는 Stage C, 디코딩은 고정 Stage C, 모델·초기화 비교는 Stage A에서 했다. 비교별 조건과 불일치를 함께 보고한다.

### 9.1 epoch를 늘리면? (6시간 12분)

Stage C가 마지막 평가에서 최고점이라 3 epoch를 시도했다.

- 결과: **−0.06 [−0.57, +0.45]** → 차이를 확인하지 못했다
- 조기 종료가 걸려 34,000/52,182 스텝에서 멈췄다. 1 epoch 이후 27 근처에서 ±0.3 흔들리며 정체했다
- 해석: 시도한 3 epoch 설정에서는 추가 이득을 확인하지 못했다. 학습률 스케줄 효과가 원인인지는 분리 실험하지 않았다

### 9.2 나머지 8종 비교 결과

| 바꾼 값 | ROUGE-L 공백 차이 (95% CI) | 판정 |
|---|---|---|
| 학습률 3e-4 (기준 1e-4) | −0.31 [−0.96, +0.37] | 차이 미확인 |
| 학습률 5e-5 | **−0.93 [−1.44, −0.41]** | **더 나쁨** |
| 유효 배치 8 (기준 16) | +0.18 [−0.27, +0.65] | 차이 미확인 (학습 시간 1.6배) |
| 유효 배치 32 | **−0.87 [−1.40, −0.40]** | **더 나쁨** |
| warmup 0% (기준 5%) | −0.22 [−0.62, +0.13] | 차이 미확인 |
| warmup 10% | −0.04 [−0.41, +0.31] | 차이 미확인 |
| label smoothing 0.0 (기준 0.1) | −0.41 [−0.87, +0.01] | 차이 미확인 (반복은 7.7→8.8% 증가) |
| 정규화 축약 끄기 | −0.21 [−0.74, +0.30] | 차이 미확인 (잘린 입력 63→102건) |
| length_penalty 1.2 (기준 1.0) | −0.01 [−0.22, +0.22] | 차이 미확인 |
| length_penalty 0.8 | **−0.44 [−0.71, −0.17]** | **더 나쁨** |

**결론: 9종을 검증했는데 기준값을 바꿀 근거가 나온 것은 하나도 없다.** 기준값이 더 낫다고 확인된 경우가 3건이다.

### 9.3 이 과정에서 배운 것 세 가지

**(1) loss가 낮다고 요약이 좋은 게 아니다**

학습률 3e-4는 train loss가 가장 낮았는데(2.615 vs 기준 2.722) dev ROUGE는 오히려 낮았다.
3 epoch 실험에서도 loss는 끝까지 내려가는데 ROUGE는 정체했다. **loss 개선을 성능 개선으로 읽으면 안 된다.**

**(2) 판별할 수 있는 차이에는 한계가 있다**

문장 bootstrap 구간은 고정된 예측의 평가 표본 변동만 반영한다. 학습 seed 변동·반복적인 dev 탐색·판정자 오차는 별개이며, 유의성 미확인은 동등성 입증이 아니다. 차이의 구간 폭은 비교하는 예측 쌍마다 달라 고정된 ±0.6점 판별 한계는 없다.
저장된 건별 점수로 beam4−beam2를 다시 비교하면 +0.516 [0.051, 0.978]이다(bootstrap 1,000회, seed 0, 반올림 CSV 기준).

**(3) 조기 종료의 판정 기준에 함정이 있었다**

개선 판정에 임계값이 없어서 **+0.001도 "개선"으로 세어** 카운터가 초기화됐다(실제 사례: 26.700 vs 26.699).
dev 점수의 평가 간 변동폭이 ±0.3~0.4인데 말이다. → 임계값을 0.1로 바꿨다. 단, 이 값 자체는 아직 비교하지 않았다.

또 하나: patience(참는 횟수)를 2로 했다면 Stage C 2 epoch run이 12,000스텝에서 멈췄을 것이고, 그때 점수는 25.74로 최종(27.33)보다 1.6점 낮다.

### 9.5 디코딩 전략 튜닝 (모델은 그대로, 생성 방식만 바꿔 비교)

모델을 다시 학습하지 않고 **생성 방식만** 바꿔가며 비교했다. 모두 같은 Stage C 모델, 같은 dev 1,500건이다.

| 전략 | 설정 | ROUGE-L 공백 | 기준 대비 | 생성 시간(1,500건) | 판정 |
|---|---|---:|---|---:|---|
| greedy | beam 1 | 25.86 | −1.60 | 131초 | 관측 평균이 낮음 |
| beam search | beam 2 | 26.94 | −0.516 [−0.978, −0.051] | 167초 | 이 예측 쌍에서 낮음 (탐색적 비교) |
| **beam search (선택)** | **beam 4** | **27.46** | — | 180초 | 기준 |
| beam search | beam 8 | (9.5.1 참조) | | | |
| 반복 금지 | nrng 3 → **0** | — | 정답의 13.37%를 막던 설정을 해제 | — | 해제 확정 |
| 길이 보정 | lp 1.2 | 27.45 | −0.01 [−0.22, +0.22] | 180초 | 차이 미확인 |
| 길이 보정 | lp 0.8 | 27.02 | **−0.44 [−0.71, −0.17]** | 180초 | 더 나쁨 |

**디코딩에서 배운 것**
1. 디코딩만으로 **1.6점**이 움직인다(greedy vs beam 4). 그래서 모델 비교는 디코딩을 고정해야 한다
2. 기본값이 항상 옳지 않다. `no_repeat_ngram_size=3`은 한국어 요약에서 **정답의 13.37%를 생성 불가능**하게 만들고 있었다
3. 길이를 정답에 맞춰도(lp 1.2, 예측 39.8자 → 41.4자, 정답 41.9자) 점수는 그대로였다. **이 길이 보정 실험에서 점수 개선을 확인하지 못했다. 길이의 인과 효과를 배제한 것은 아니다**

### 9.6 모델 비교 — pko-T5 vs KoGPT2 (구조 효과 미분리)

5.3절의 모델 선택을 보조하기 위해 pko-T5와 KoGPT2의 제한된 조건 비교를 수행했다. 구조 자체의 효과는 확인하지 못했다.
같은 데이터(2,000건)·같은 dev·같은 유효 배치·같은 epoch·같은 beam 4로 두 구조를 학습했다.

| 구조 | 모델 | 파라미터 | 학습률 | 반복금지 | ROUGE-L space | 반복 4-gram | 학습 | VRAM |
|---|---|---:|---|---:|---:|---:|---:|---:|
| **인코더-디코더 (선택)** | pko-t5-base | 275.6M | 1e-4 | 0 | **22.63** | 8.2% | 12.5분 | 7.15GB |
| 디코더 전용 | KoGPT2 | 125.2M | 5e-5 | 0 | 14.71 | **23.6%** | 2.0분 | 4.42GB |
| 디코더 전용 | KoGPT2 | 125.2M | 1e-4 | 0 | 13.64 | 20.7% | 1.9분 | 4.42GB |
| 디코더 전용 | KoGPT2 | 125.2M | 5e-5 | **3** | 13.18 | **0.0%** | 2.8분 | 4.42GB |

**디코더 전용을 학습시키려고 따로 처리한 것** (`src/train_decoder.py`)
1. 대화와 요약을 한 줄로 이어 붙인다: `<대화>
요약: <요약></s>`
2. **손실은 요약 부분에만** 건다. 대화 부분 라벨을 −100으로 가리지 않으면 대화를 외우는 데 학습이 쓰인다
3. 생성할 때는 프롬프트만 넣고 뒤에 붙은 생성분만 잘라낸다. 배치 생성을 위해 **왼쪽 패딩**을 쓴다
4. KoGPT2는 토크나이저의 `</s>` id가 51200인데 임베딩 행은 51200개(0~51199)여서 그대로 쓰면 인덱스 오류가 난다 → **임베딩을 51,201행으로 확장**

**결과 해석**
- 시험한 조건에서 pko-T5가 **+7.9점** 높았다. 이 격차가 구조 자체에서 비롯됐다고 말할 수는 없다
- 디코더 전용은 **반복 붕괴**가 특징이다: `반지가 반짝반짝 반짝 반짝 반짝 …` (반복 4-gram 23.6%, 정답 0.53%)
- 반복 금지(nrng 3)를 켜면 반복은 0%가 되지만 **점수는 더 내려간다**(14.71 → 13.18). **이 반복 금지 설정으로 ROUGE 개선을 얻지 못했다. 원인 관계는 미확인이다**
- 반복률은 각 모델 토크나이저 기준이다. T5는 예측 8.2%/정답 6.53%, KoGPT2는 예측 23.6%/정답 0.53%이며 모델 간 직접 비교하지 않는다
- 자원은 디코더 전용이 훨씬 가볍다 (학습 2분 vs 12.5분, VRAM 4.42GB vs 7.15GB). 점수를 포기할 수 있다면 선택지가 된다

**이 비교의 한계 (그대로 적는다)**

추가 공정성 한계: 토크나이저와 사전학습 조건이 다르고, T5는 dev 기준 best checkpoint(300스텝), KoGPT2는 마지막 상태(375스텝)를 평가했다. KoGPT2의 기존 실행 코드는 config의 label smoothing 0.1을 전달하지 않아 실제로는 기본값 0.0을 사용했다. 반복 4-gram도 모델별 토큰 단위여서 직접 비교할 수 없다(정답 반복률 T5 6.53%, KoGPT2 0.53%). 따라서 결과는 두 모델과 실행 절차의 비교이며 구조 자체의 인과 효과가 아니다. 2026-09-21 코드 정정으로 smoothing 전달과 프롬프트 잘림 방향을 수정했으나 재학습하지 않았고, 표의 기존 점수는 수정 전 실행 결과다.

1. 파라미터가 다르다 (275.6M vs 125.2M). 같은 크기의 한국어 디코더 전용 공개 모델을 찾지 못했다
2. 2,000건 규모에서만 비교했다. 규모가 커지면 순서가 바뀔 수 있다
3. 프롬프트 형식을 한 가지(`
요약: `)만 시도했다

## 11. 한계 — 무엇을 확인하지 못했나

이 프로젝트에서 **하지 않은 것과 모르는 것**을 명시한다.

1. **사실 오류가 남아 있다** (100건 중 15건). 그래서 이 모델을 "최종 모델 확정"이라고 부르지 않는다
2. 오류 판정자는 **Claude 1인**이다. 사람 판정과 얼마나 다른지 모른다
3. **시드 1개**로만 학습했다. 같은 설정으로 다시 돌렸을 때의 편차를 재지 않았다. 따라서 학습 seed에 따른 성능 변동은 정량화하지 못했다. 문장 bootstrap 구간과는 별개다
4. 가이드라인 관련 자동 점검은 **규칙 기반 근사**다. "육하원칙 2요소" 조건은 판정하지 않았다
5. **토론 대화 형식**은 배우지 못했다 (test 188건, 4.79%)
6. **긴 대화에서 점수가 낮은 원인**을 확인하지 않았다
7. 학습 직후 평가와 평가 스크립트의 **0.13점 차이 원인**을 확인하지 못했다
8. 시스템 다운의 **정확한 원인**을 확정하지 못했다 (VRAM 초과 추정, 하드웨어 문제 가능성)
9. Stage 간 비교 중 A→B는 **변수가 두 개**(데이터·epoch) 바뀌었다
10. test는 이미 사용했다. 앞으로 개선해도 **test로 다시 확인할 수 없다**

| 5 | **loss ≠ 성능** | 학습률 3e-4가 loss는 최저인데 ROUGE는 더 낮음 | 모델 선택은 항상 dev ROUGE로 (9.3절) |
| 6 | **조기 종료가 노이즈에 속음** | +0.001 개선으로도 patience 카운터가 초기화 | `early_stopping_threshold` 0.1 도입 |
| 7 | **체크포인트가 디스크를 먹음** | 체크포인트 1개 = 모델 1.1GB + 옵티마이저 상태 ≈ 3.3GB | `save_total_limit: 2`, 끝나면 best만 남기고 삭제 |
| 8 | **긴 학습은 반드시 끊긴다고 가정** | 6시간 학습 중 다운되면 전부 날아감 | `--resume` 구현 + 강제 종료 테스트로 검증 (6.7절) |
| 9 | **같은 모델인데 점수가 다름** | 학습 직후 평가 27.325 vs 평가 스크립트 27.456 | 원인 미확인. **보고 경로를 하나로 통일**하고 그 사실을 기록 (7.6절) |
| 10 | **평균이 약점을 숨김** | 전체 27.15인데 토론 대화만 16.02 | 주제·유형·길이·참여자 수로 쪼개서 보기 (7.4절) |

## 부록 B. 이 프로젝트에서 지킨 보고 규칙

숫자를 다루는 방식 자체를 규칙으로 정해 두고 지켰다. 발표에서 "어떻게 일했는가"로 쓸 수 있는 부분이다.

1. **한 번에 한 변수만** 바꾼다. 불가피하게 둘이 바뀌면 그렇게 기록한다 (Stage A→B의 epoch 변화)
2. 차이는 **95% 구간**으로 말한다. 구간이 0을 포함하면 "차이를 확인하지 못했다"고 쓴다. "약간 좋다"고 쓰지 않는다
3. 토큰화 기준(공백/형태소)과 디코딩 설정(beam 수 등)을 **항상 함께** 적는다
4. 학습 데이터로 잰 점수는 "성능"이 아니라 **"재현 점검"**이라고 쓴다
5. **test는 1회.** 코드로 잠갔다
6. 확인하지 않은 것은 **"확인하지 않았다"**고 쓴다. 추정을 결과처럼 쓰지 않는다
7. 사실 오류가 남아 있으면 점수가 올랐어도 **"최종 모델 확정"이라고 쓰지 않는다**
8. 모든 실행은 설정·로그·지표·예측을 남긴다. 결론은 산출물로 다시 검증할 수 있어야 한다
