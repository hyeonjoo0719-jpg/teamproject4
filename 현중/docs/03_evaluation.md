# 03. 평가 프로토콜

> **2026-09-21 검토 반영:** 자동 점검 통과율은 전체 가이드라인 준수나 사실 정확성이 아니며, 표본 오류 분류는 Claude 단독 판정이다. test는 2026-09-20 00:14 당시 고정한 Stage C 후보에 대해 1회 평가했다. 이후 test에서 관찰한 토론 문제 등을 참고해 dev에서 추가 탐색했다. 후속 개선은 독립 test 검증을 받지 않았으며 새 holdout이 필요하다.

**규칙: 토큰화 기준과 디코딩 설정을 함께 적지 않은 점수는 기록하지 않는다.**
두 점수를 비교할 때는 데이터·토큰화·디코딩이 모두 같은지 먼저 확인한다.

---

## 1. 주 지표 — ROUGE

`rouge-score` 패키지를 쓰되, 한국어에 맞게 토큰화를 직접 지정한다.

| 지표 | 의미 |
|---|---|
| ROUGE-1 | 단어(uni-gram) F1 |
| ROUGE-2 | 2-gram F1 — 어순·표현 일치 |
| ROUGE-L | 최장 공통 부분수열 F1 — **주 지표** |

**토큰화 2종을 모두 보고한다.**

1. `space` — 공백 기준. 계산이 빠르고 재현이 쉽다. **기본 보고값**
2. `morph` — 형태소 기준(`kiwipiepy` 권장). 조사·어미 차이에 덜 민감한 어휘 겹침 지표이며 의미·사실 일치를 보장하지 않는다

같은 모델이라도 두 기준의 점수는 다르다. 표에 기준을 열로 넣는다.

**점수 계산 전 문자열 정규화 (Part 3에서 결정)**: 예측과 정답 **양쪽 모두** `unicodedata.normalize("NFKC", s)`를 적용하고 앞뒤 공백을 정리한 뒤 토큰화한다.

- 이유: `pko-t5` 토크나이저의 normalizer가 NFKC다. 모델 출력은 항상 NFKC 형태로 나오는데, 정답의 0.14%(train 10만 건 중 142건)는
  NFKC 전후가 다르다(줄바꿈 없는 공백 U+00A0 134건, 호환 자모 `ㅋ`→`ᄏ` 등). 정규화하지 않으면 정답과 완전히 같은 출력도 점수가 깎인다
- 이 정규화는 **점수 계산용**이다. 학습 데이터의 정답 파일은 바꾸지 않는다 (토크나이저가 학습 라벨에 이미 NFKC를 적용한다)

참고선: 가이드라인 시범 모델은 ROUGE-1 20.872 / ROUGE-2 9.156 / ROUGE-L 19.547.
단, 원문에 토큰화 기준이 없다. **비교가 아니라 참고선**으로만 인용한다.

## 2. 보조 지표 — 규칙 기반 자동 점검 통과율

`src/guideline_check.py`로 생성 요약문마다 자동 판정한다. 각 항목은 0/1이고 전체 비율을 보고한다.

| 항목 | 판정 규칙 | 근거 |
|---|---|---|
| 한 문장 | 문장 종결 부호로 분리했을 때 1문장 | 가이드라인 "한 문장으로 요약" |
| 태그 없음 | `#@...#` 패턴이 없음 | "요약문에는 비식별화된 항목을 포함하지 않는다" (실측 위반 0건) |
| 길이 정상 | 10 ~ 150자 | 프로젝트 자체 검토 범위. train 요약 길이는 평균 42자, 최대 174자이며 150자는 가이드라인 상한이 아님 |
| 키워드 겹침 | 대화 원문의 내용어 2개 이상이 요약에 등장 | "키워드 2개 이상 포함" 조건 |
| 반복 없음 | 같은 3-gram이 2회 이상 반복되지 않음 | 생성 모델 흔한 실패 |
| 종결 형식 | 일상 대화는 "~다"로 끝남 | "~하다/한다" 형식 |

토론 대화 슬라이스에는 추가로 "토론한다" 류 표현 포함 여부를 본다(188건뿐이라 참고치).

## 3. 슬라이스 평가

전체 평균만 보면 편향이 숨는다. 아래 단위로 나눠 본다.

- **주제별 9개** — 건수가 적은 시사/교육(4.7%)이 특히 나쁜지 확인
- **유형별 2개** — 토론 대화는 0.54%뿐이다. 점수가 낮은 원인은 데이터 불균형 등을 가설로만 기록한다
- **대화 길이 3분위** — 짧은 대화에서 정보 부족으로 무의미한 요약이 나오는지
- **참여자 수** — 2인(93%) vs 3인 이상. 화자 혼동은 주로 3인 이상에서 난다

## 4. 모델 비교 — paired bootstrap

두 모델 점수 차이를 그냥 빼서 비교하지 않는다.

1. 같은 평가셋에서 두 모델의 문장별 점수를 구한다
2. 문장 인덱스를 복원 추출로 리샘플(1,000회)해 차이 분포를 만든다
3. 2.5 / 97.5 백분위로 **95% 신뢰구간**을 낸다
4. 구간이 0을 포함하면 "차이를 확인하지 못했다"고 쓴다. "비슷하다"거나 "약간 좋다"고 쓰지 않는다

## 5. 표본 대조 (현재 Claude 단독 판정, 사람 검증 미실시)

**고정된 30건**을 정해두고 매 모델마다 같은 30건을 대조한다. 매번 다른 표본을 쓰면 비교가 안 된다.

각 건에 대해 오류 유형을 붙인다(복수 가능).

| 유형 | 설명 |
|---|---|
| 사실 오류 | 대화에 없는 내용, 주체·대상 뒤바뀜 |
| 핵심 누락 | 대화의 중심 사건이 빠짐 |
| 반복 | 같은 구절 되풀이 |
| 화자 혼동 | 누가 한 말인지 뒤섞임 |
| 형식 위반 | 두 문장, 태그 포함, 종결 형식 어긋남 |
| 무난 | 문제 없음 |

ROUGE가 올랐어도 사실 오류 비율이 그대로면 **개선이라고 쓰지 않는다.**

## 6. 디코딩 설정

디코딩은 성능 보고와 분리한다. 비교 실험에서는 **모든 모델에 같은 디코딩 설정**을 쓴다.

| 설정 | 기본값 |
|---|---|
| num_beams | 4 |
| max_new_tokens | 64 |
| no_repeat_ngram_size | **0** (2026-09-19 변경: 3은 정답의 13.4%를 생성 불가능하게 만든다. `04_experiment_log.md`) |
| length_penalty | 1.0 |
| early_stopping | True |

greedy(빔 1) 점수도 함께 기록해두면 모델 자체의 개선인지 디코딩 효과인지 구분된다.

## 7. 보고 형식

`artifacts/eval/<run>/RESULT.md`에 아래 항목을 모두 넣는다.

1. 모델·체크포인트 경로, 학습 데이터 규모, config 해시
2. 평가셋 이름과 건수 (dev인지 test인지 명시)
3. 토큰화 기준별 ROUGE-1/2/L 표
4. 규칙 기반 자동 점검 통과율 표
5. 슬라이스별 점수 표
6. 비교 대상이 있으면 paired bootstrap 95% 구간
7. 생성 예시 5건 (원문 / 정답 / 생성)
8. 오류 분류 30건 요약
9. 한계 — 무엇을 확인하지 못했는지

## 8. 금지 사항

- 학습 데이터 점수를 성능으로 보고하지 않는다
- test 최초 평가 전에는 내용 열람을 제한하고, 평가 이후 결과를 참고한 탐색은 독립 검증과 구분한다
- 토큰화 기준이 다른 점수를 같은 표에 나란히 두지 않는다
- 신뢰구간 없이 "개선됐다"고 쓰지 않는다
- 사실 오류가 남아 있는데 "최종 모델 확정"이라고 쓰지 않는다


### 통계 해석 보충 (2026-09-21)

문장 bootstrap 구간은 고정된 예측의 평가 표본 변동만 반영한다. 학습 seed 변동·반복적인 dev 탐색·판정자 오차는 별개이며, 유의성 미확인은 동등성 입증이 아니다. 차이의 구간 폭은 비교하는 예측 쌍마다 달라 고정된 ±0.6점 판별 한계는 없다.
