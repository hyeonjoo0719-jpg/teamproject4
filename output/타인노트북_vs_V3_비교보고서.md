## 4. 타인 노트북의 좋은 점

타인 노트북은 단순 학습 파일보다 연구용 워크북에 가깝다. 다음 기능은 V3에 추가할 가치가 있다.

1. 길이 그룹 배칭으로 padding 연산을 줄인다.
2. 중간 평가에서 생성 품질을 함께 관찰한다.
3. bootstrap 신뢰구간과 대응 bootstrap으로 점수 차이의 불확실성을 계산한다.
4. 토론 대화를 별도 집단으로 평가한다.
5. 입력 잘림, 정답 추상성, 생성 길이와 건별 점수의 관계를 분석한다.
6. 사람이 채점할 CSV와 채점 후 ROUGE 상관 분석 코드를 제공한다.
7. optimizer와 scheduler를 포함한 재개 체크포인트를 저장한다.
8. 저장 후 재로딩했을 때 출력이 같은지 확인한다.
9. 실험 기록, 배치 추론, API 초안까지 포함한다.

## 5. 타인 노트북에서 주의해야 할 문제

### 5.1 그대로 실행하면 본 학습이 아니다

설정 셀의 기본값은 `cfg.smoke_test = True`다. 이 상태에서는 학습 데이터 2,000건, 최대 60 step, 최종 평가 100건으로 바뀐다. 끝까지 매우 빨리 실행돼도 정상이며, 그 결과로 모델 성능을 판단하면 안 된다.

smoke test를 끈 뒤에도 기본 학습은 40,000건×3 epoch다. V3의 실제 학습은 265,000건을 약 1.3회 본 양이므로, 기본 설정끼리 비교하면 v8의 학습 데이터 노출량이 훨씬 작다.

### 5.2 전달받은 파일에는 실제 실행 결과가 없다

57개 코드 셀의 `execution_count`가 모두 비어 있고 출력도 0개다. 문서에 “실측”이라고 적힌 수치가 많지만, 현재 파일에서 재현된 출력은 아니다.

특히 §11.2 앞의 참고 결과는 KoBART가 아니라 “12M 파라미터 BART, from scratch, CPU 2코어, 2,700 step, test 700건” 결과다. V3의 124M KoBART·35,004건 평가와 직접 비교할 수 없다.

### 5.3 `stemsub`는 표준 ROUGE가 아니다

`stemsub`는 예측과 정답에서 어간 집합을 만든 뒤, 공백을 제거한 상대 문자열에 해당 어간이 부분문자열로 존재하는지 센다. 단어 빈도와 순서를 무시하며 ROUGE의 n-gram 또는 LCS 정의와 다르다.

코드는 이 값 하나를 `rouge1`, `rouge2`, `rougeL` 세 칸에 똑같이 넣는다. 따라서 “stemsub ROUGE-L”이라는 이름은 오해를 부른다. 사용할 수 있는 사용자 정의 어휘 겹침 지표이지만 보고서에는 `StemSub-F1`처럼 별도 이름으로 표시해야 한다.

또한 띄어쓰기 변형과 같은 주제의 무관 요약으로 보정했을 뿐 사람 평가와의 상관으로 검증하지 않았다. 이 지표가 “품질 변별력이 가장 높다”고 확정하기에는 근거가 부족하다.

### 5.4 추출 oracle과 모델 점수를 서로 다른 지표로 비교한다

`extractive_oracle()`의 기본 `mode`는 `stem`인데 출력 문구에는 `cfg.select_metric`인 `stemsub` 기준이라고 표시된다. 이후 모델의 stemsub 점수와 이 stem oracle을 직접 비교한다. 서로 다른 계산법의 숫자이므로 “oracle 초과” 여부를 판정할 수 없다.

게다가 이 oracle은 모든 추출 요약의 이론적 상한이 아니라 연속 1~3개 발화만 고르는 제한된 방식의 최고점이다. 이를 넘었다고 곧바로 “진짜 추상 요약”이라고 결론 내릴 수 없다.

### 5.5 ‘사람 상한 약 40’은 신뢰할 수 있는 상한이 아니다

서로 독립적으로 배정된 동일 원문의 복수 정답을 사용한 것이 아니다. MinHash로 비슷한 대화 6쌍을 찾아 서로 다른 요약을 비교한 값이다. 일부 쌍은 원문 자체가 완전히 같지 않다고 문서도 인정한다. 표본도 6쌍뿐이므로 사람 성능의 상한이나 모델의 사람 대비 비율로 쓰기 어렵다.

또한 MinHash 입력에 Python의 내장 `hash()`를 사용한다. 노트북 안에서 `PYTHONHASHSEED`를 설정해도 이미 시작된 Python 프로세스의 hash seed는 바뀌지 않으므로 커널을 다시 열면 후보 쌍이 달라질 수 있다. SHA-256처럼 안정적인 해시로 바꾸어야 한다.

### 5.6 smoke test도 전처리는 가볍지 않다

학습 표본을 2,000건으로 줄이기 전에 Training과 Validation 전체를 DataFrame으로 읽고, 두 split 전체 약 31.5만 건을 모두 토큰화해 pickle로 저장한다. 전수 EDA·품질 검사·근접 중복 검사도 실행한다. 따라서 “전 구간 3분”은 PC와 캐시 상태에 따라 성립하지 않을 수 있다.

### 5.7 기본 batch 32가 먼저 실행된다

선택형 최대 배치 탐색 셀보다 앞에서 batch 32로 실제 forward/backward 벤치마크를 수행한다. GPU 메모리가 부족하면 자동 탐색에 도달하기 전에 실패한다. 사용자 GPU에 맞춰 작은 배치로 시작하거나 OOM 재시도를 벤치마크 앞에 넣어야 한다.

### 5.8 split 누수 통제가 V3보다 약하다

ID 교집합은 확인하지만 정규화 원문 SHA-256으로 Train/Validation 간 정확 중복을 제거하지 않는다. MinHash 검사는 진단용이며 실제 분할에서 제거하지 않는다. 선택된 행의 manifest도 저장하지 않으므로 나중에 정확히 같은 분할인지 감사하기 어렵다.

### 5.9 API가 노트북 추론과 완전히 같지 않다

노트북의 `generate_summaries()`는 생성 후 마스킹 토큰 제거, 공백 정리, 마침표 추가를 수행한다. 생성하는 `serve.py`는 단순 decode와 strip만 수행한다. 제공된 parity 검사는 입력 전처리만 비교하므로 이 출력 후처리 차이를 잡지 못한다. 배포 전 `postprocess()`를 API에도 그대로 넣고 최종 문자열 일치 검사를 해야 한다.

## 6. V3의 약점

V3의 실행 결과가 있다는 것과 분석이 완성됐다는 것은 다르다. 다음 부분은 보강해야 한다.

1. 평균 점수에 bootstrap 신뢰구간이 없다.
2. 한 번의 seed만 실행해 학습 변동성을 모른다.
3. `human_review.csv`는 만들었지만 사람이 아직 채점하지 않았다.
4. 체크포인트 선택이 2,048건 개발 loss 기준이고 생성 품질 기준은 아니다.
5. 정확한 optimizer·scheduler·난수 상태 재개를 지원하지 않는다.
6. 토론 대화가 188건뿐이고 어절 R-L 12.03으로 일상 대화 23.25보다 크게 낮지만, 원인을 세분화하지 않았다.
7. 사실성·화자 혼동·핵심 누락을 자동 지표만으로 충분히 평가하지 않았다.
8. 최종 생성이 greedy라 개발 표본의 beam 4보다 약 1.23점 낮았다.

## 8. 발표 때 사용할 결론

다음과 같이 설명하면 정확하다.

> 타인 노트북은 통계 분석, 오류 분석, 재개 학습, 배포 코드까지 포함한 확장형 연구 템플릿이다. 그러나 전달받은 파일은 실행되지 않았고 기본값도 60 step smoke test이므로 성능 결과는 없다. 일부 사용자 정의 지표와 상한 해석에는 방법론적 오류가 있어 그대로 인용할 수 없다. 우리 V3는 기능 수는 적지만 265,000건으로 실제 학습했고, 7시간 안에 공식 Validation 35,004건 전체를 평가해 가장 긴 발화 기준선보다 어절 ROUGE-L이 5.88에서 23.19로 향상됐다는 재현 가능한 결과가 있다. 이후에는 상대 노트북의 신뢰구간, 토론 분석, 사람 평가, 재개 체크포인트 같은 장점을 검증된 방식으로 선택해서 추가하는 것이 좋다.
